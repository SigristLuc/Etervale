# monogame/: MonoGame v3.8.6 fork (Vulkan)

Etervale renders with MonoGame's Native platform on Vulkan through this fork. Both halves of MonoGame that the client
runs are kept here as source: the native runtime (`runtime/`), the framework built from source (`framework/`) and the
SM 6 effect processor (`pipeline/`). There is no git submodule and no NuGet package for the framework; third-party code
is pinned by commit. Nothing machine-built is committed: the native library is built by `runtime/build.sh` (Linux,
macOS) or `runtime/build-windows.ps1` (Windows), and the C# projects by `dotnet build`.

| Folder | What | Built by |
|---|---|---|
| `runtime/` | The native runtime (C++: Vulkan, SDL2, FAudio): MonoGame's `native/monogame` with the fork's changes, the record of them as `monogame-v3.8.6.patch`, `externals.txt` (pinned dependencies), the build scripts, `repro/` (verification programs). | `runtime/build.sh`, `runtime/build-windows.ps1` → `runtime/bin/<rid>/` (git-ignored) |
| `framework/` | `MonoGame.Framework` (C#), Native platform only, from source; a project reference of the client libraries. | `dotnet build` (in `PristonTale.sln`) |
| `pipeline/` | The effect processor MGCB runs for the client's shaders (`SpirvEffectProcessor`) and the Vulkan effect compiler under it, from MonoGame's source: compute passes, storage resources, SM 6.5 profiles, MGFX 12. | `dotnet build` (in `PristonTale.sln`; the client builds it before its content) → `pipeline/bin/` (git-ignored) |
| `issues/` | One document per change of the fork: the symptom or need, the cause, the change, the test. | — |
| `upstream/` | One note per runtime fix, written as material for an issue the owner may file himself (MonoGame accepts no AI-written contributions, so nothing is sent upstream as a pull request). | — |
| `LICENSE-MonoGame.txt` | MonoGame's licence, the Microsoft Public License, for everything under `monogame/` except the third-party code credited in each part's `CREDITS.md`. | — |

## How Etervale uses it

- The client libraries reference `framework/MonoGame.Framework/MonoGame.Framework.Native.csproj` as a project.
- The client references the processor (`pipeline/MonoGame.Effect.Processor`) without its assembly, so it is built before
  `Client/PristonTale/Content/Content.mgcb` loads it.
- `Client/MonoGameRuntime.targets` requires `runtime/bin/<rid>/` and copies the library next to the client and the
  regression runner.
- Built files (`runtime/bin`, `runtime/build`, the fetched SDL2 and FAudio, `pipeline/bin`) are git-ignored and never
  committed.

## Version

- Upstream: https://github.com/MonoGame/MonoGame, tag **v3.8.6** (commit `c610a529667336f63da323c6057274258727664b`),
  for both halves. How each was taken from the tag: [runtime/README.md](runtime/README.md) and
  [framework/README.md](framework/README.md).
- Third-party code is pinned by commit: `runtime/externals.txt` (volk, VMA, Vulkan headers, stb vendored; SDL2 and FAudio
  fetched by the build scripts), [framework/CREDITS.md](framework/CREDITS.md) (StbImageSharp, StbImageWriteSharp
  vendored), [pipeline/CREDITS.md](pipeline/CREDITS.md) (CppNet vendored).
- Updating MonoGame is a deliberate change: the new tag's files in every part, the fork's changes reapplied (the patch,
  the `Etervale fork` markers in the C#, `issues/`), every platform rebuilt, and the compiled effects and rendered
  frames compared before and after.

## Rules for changing it

- **Every change has a document.** A change of behaviour gets a numbered document in `issues/` (symptom or need, cause,
  change, test) and, in the runtime, an entry in the change list of [runtime/README.md](runtime/README.md). A runtime
  fix that also applies to upstream MonoGame gets a note in `upstream/`.
- **The C# changes are marked.** Every edit of upstream code in `framework/` and `pipeline/` carries an `Etervale fork`
  comment; `runtime/monogame-v3.8.6.patch` is regenerated by `runtime/regenpatch.sh` after a change to `runtime/src/`.
- **The framework and the runtime are one version.** A change to the runtime's exports raises the interface version in
  both halves: `MGVK_ETERVALE_RUNTIME_VERSION` in `runtime/src/vulkan/MGG_Vulkan.cpp` (returned by
  `MGG_Etervale_RuntimeVersion`) and `EtervaleRuntimeVersion` in
  `framework/MonoGame.Framework/Platform/Native/Graphics.Interop.Etervale.cs`. The framework checks it when it creates
  the graphics system and stops with instructions on a mismatch
  ([issues/002-runtime-version.md](issues/002-runtime-version.md)).
- **Rebuild after a change.** Any change under `runtime/src/` needs the native library rebuilt before the client: see
  the Build section of [../README.md](../README.md#build).
- **Generic GPU facilities are the fork's public API** (frame capture, timestamps, compute, storage resources); what is
  specific to the game (its checks, profilers and effects) stays in the game's code.
- **Every warning is an error here too.** The C# builds with MonoGame's compiler settings and `TreatWarningsAsErrors`
  (`framework/Directory.Build.props`, `pipeline/Directory.Build.props`); the C++ with the warning settings of
  `runtime/src/premake5.lua`.

The fork's GPU API beyond XNA: `GraphicsDevice.BeginFrameCapture`/`TryPopFrame` (issue 003), `GpuTimestampPool` (004),
`GraphicsDevice.Dispatch`/`DispatchIndirect`, `EffectPass.IsCompute`, `Texture2D` with `TextureShaderAccess.ReadWrite`
(005), `StructuredBuffer` (006), MGFX 12 and the `cs_6_0`/`*_6_5` profiles (007, 008), pipeline statistics (012),
NoOverwrite uploads in place (013) and the clipboard's text (`Input.Clipboard.GetText`, 014).
